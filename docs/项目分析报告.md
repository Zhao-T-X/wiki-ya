## 2. 产品定位

一句话：**以 Ontology 为核心、以 Evidence 为依据、以 Evolution 为历史、以 Context Efficiency 为 AI 基础设施的 Local-first Personal Knowledge System。**

形态：桌面端（Tauri），单人、本地优先、无需账号即可用。

它刻意与四类产品划清界限：不是传统 Wiki、不是笔记软件、不是 Chatbot、不是单纯知识图谱。差异化的锚点是**"知识演进 + 证据"**，而不是"存得多"或"搜得快"。

### 六条产品理念（决定后续所有设计取舍）

| 理念 | 含义 | 对应工程规则 |
|---|---|---|
| Capture first. Organize later. | 用户只负责输入，分类/建模由系统做 | 抽取与归一化必须自动化 |
| Never silently overwrite | 新知识不得覆盖旧知识，只能建立演化关系 | 禁止直接 `UPDATE status` |
| Evidence is part of knowledge | 知识 = Claim + Evidence + Source + Time | Evidence 一等公民 |
| AI suggests, user decides | AI 无知识库写权限 | 提案 → 校验 → 审核 → 提交 |
| Deterministic logic first | Schema/归一化/方向/事务归程序，语义归 LLM | Domain 层不依赖 AI |
| Complexity in system, not UI | 用户看到"这条知识可能更新了已有知识" | 一级导航不暴露 Ontology/Agent |

## 3. 核心闭环与一级模块

```
Capture → Understanding → 对照已有知识 → Evolution 分类
        → (New/Duplicate/Supplement/Conflict) → Review → Commit
        → Knowledge / Graph / Search → Ask / Research → 再次 Capture
```

一级导航固定为 8 个：`Inbox / Knowledge / Search / Review / Ask / Research / Graph / Settings`。

关键取舍：
- **Graph 不是首页**，只在 Entity 详情里作为"探索"入口，避免默认加载全图。
- **Agent / Ontology / Context Runtime 不进入一级导航**，`role=auto` 由 Router 决定。
- **Inbox 有明确状态机**：`captured / processing / understood / review_required / committed / failed / archived`。

## 4. 领域模型（Ontology = Domain Core）

| 对象 | 职责 | 边界 |
|---|---|---|
| Document / Raw | 真相来源，永久保留、不可变 | 结构化知识永远不能覆盖它 |
| Chunk | 内部计算单位（含 offset / hash / embedding） | 用户默认不操作 |
| Entity | 稳定对象（Rust、Tauri、SQLite…） | 有 canonical name / aliases / type / status |
| Entity Type | 受控注册表、版本化 | **不允许 LLM 自由创造** |
| Predicate | 受控注册表 | 定义 domain / range / inverse / symmetric / transitive / conflict_rules / normalization_rules |
| Claim | 知识的核心单位 | `subject + predicate + object + polarity + modality + claim_type + confidence + status + valid_from/valid_until + recorded_at` |
| Relation | Entity → Entity | 与 Claim 不混淆 |
| Event | 发生过的事（Rust 1.85 released） | 含 time / evidence |
| Idea | 尚未成为事实的思考 | 不强制转 Claim |
| Question | 未解决问题 | 可进入 Research |
| Evidence | Claim ↔ Source 的桥 | 指向 Chunk 的 offset + quote + evidence_level |

**演化关系只有 5 种**：`duplicate / coexists / supplements / supersedes / contradicts`。
**Temporal 三时间戳**让"历史正确"与"当前正确"并存，`Current Knowledge` 是**派生结果**而非副本。

**Conflict 判定链条**（向量相似度 ≠ 冲突）：
`Candidate Retrieval → Entity Resolution → Predicate Matching → Polarity → Temporal Context → Ontology Rule → Semantic Comparison`

## 5. 架构分层与依赖规则

```
React UI (Tiptap / Zustand / Tailwind / shadcn)   ← 只调 Commands
        ↓ Tauri IPC
Application (Commands / UseCases / Services / Events)
        ↓
Domain Core (Ontology / Knowledge / Evolution / Evidence / Graph / Review)
        ↓
Infrastructure (SQLite / FTS5 / Vector / Files / Cache)

AI Runtime (AgentScope Rust)  →  Application  →  Domain
```

**四条硬性禁止**：`Domain→AgentScope`、`Domain→Tauri`、`Domain→React`、`Agent→SQL`。

评价：这是整个设计中最扎实的部分。Domain 纯净 → 可单元测试、可脱离 UI 演进；AI 只能单向下行调用 Application → 保证"AI 不拥有写权限"不是口号而是结构约束；Agent 工具白名单中明确 `禁止 execute_sql`。

## 6. 关键技术机制

### 6.1 Knowledge Compiler（写入主链路）
`Raw → Parse → Chunk → Extract → Schema Validate → Normalize → Entity Resolve → Evidence Validate → Candidate → Retrieve Existing → Compare → Evolution Proposal → Review → Commit`

三处强约束：
- LLM 输出必须过 JSON Schema + serde + Domain 校验，**不直接构造 Domain 实体**；
- Entity Resolution 顺序为确定性优先（Exact → Normalized/Alias → Fuzzy → Semantic），Semantic 只能产出 `EntityMergeProposal`；
- 一切状态变化必须经 `EvolutionService`。

### 6.2 Retrieval（读取主链路）
`FTS5 + Vector + Ontology + Graph` 四路候选，经 **RRF** 融合，再叠加 Relevance / Confidence / Recency / Evidence。
向量侧 MVP 刻意不引入外部 Vector DB：SQLite + float32 blob + 本地 cosine，后续才抽象 `trait VectorStore`。
检索受 `RetrievalBudget`（max_candidates / max_claims / max_evidence / max_tokens）约束。

### 6.3 Context Efficiency Engine（AI 成本底座）
组件：Token Budget、Planner、Compiler、Pack、Dedup、Compression、History Compression、Tool Compression、Evidence Escalation、Context/Tool/Prefix Cache、Context Trace。

三条最聪明的设计：
- **LoadStrategy 四态**（`LOAD / SUMMARIZE / RETRIEVE_LATER / NEVER_LOAD`）——把"不加载什么"显式化（如 SQLite Schema → NEVER_LOAD）；
- **IDs are cheaper than payloads**——工具只返回 Decision Card（id/title/type/score/status），详情再 drill down，并带 `truncated + hint` 截断契约；
- **Cache Key = 多版本指纹哈希**（prompt/skill/reference/ontology/schema/history/task_packet），版本变则 key 变，**无需手工失效**。

同时把 Context 的预算、实际、裁剪、命中全部落库（`context_runs` / `context_sections`），并用 `Context Inspector` 向高级用户解释"为什么加载了它"以及"故意没加载什么"。

### 6.4 Agent 层
6 个内部角色（Personal / Knowledge / Research / Curator / Review / Extraction），用户侧 `role=auto`。
跨 Agent 只传 **TaskPacket**（传状态不传完整上下文）。
事件模型支撑 AG-UI 流的 SSE 式前端（文本流、工具调用、推理事件、状态快照）。
Research 结果**不能自动污染 Knowledge**，必须走 Review。

## 7. 工程约束与质量门槛

- **事务边界**：所有知识提交在 Application 层开事务，`commit_evolution()` 内包含 Create Claim / Evidence / ClaimRelation / Update Derived State / Review Decision / Event，全成功才 commit。
- **幂等**：Document Import、Claim Commit、Embedding、Extraction、Review Commit、Evolution Commit，依赖 `content_hash / source_hash / proposal_id / operation_id`。
- **派生 vs 不可丢**：FTS / Embeddings / 各类 Cache 可重建；Documents / Claims / Evidence / Relations / Reviews / History 不可丢。
- **DoD**：Domain + Persistence + Application + UI + Test + Error Handling + Observability 七项齐全才算完成。
- **关键 Domain 测试（最该守住的 7 条）**：duplicate/coexists/supplements 不改旧 Claim；supersedes 使旧 Claim 不再 current；contradicts 不删除任何 Claim；reject 不改 Knowledge；revert 能恢复。
- **性能目标**：本地 Search <100ms、Entity/Claim Lookup <20ms、FTS <100ms、Graph <200ms（AI 不计入）。
- **Token 目标**：Search 工具输出 ↓80%+、Entity ↓40%+、Graph ↓90%+、QA Context ↓70%+，以 provider 真实 usage 为准。
- **安全/隐私**：API Key 进 OS Secure Storage（禁止明文 SQLite）；默认只发送被选中的 Claim/Evidence/Chunk，禁止默认发送整库、整图、整段历史。

## 9. 设计亮点

1. **把"不覆盖历史"做成结构化机制**，而不是靠提示词约束 LLM——这是同类产品极少做到的。
2. **确定性优先的双轨制**清晰：程序管 Schema/方向/事务/状态机，LLM 管语义抽取与比较，职责不重叠。
3. **Current Knowledge 派生**而非冗余存储，天然消除一致性 bug。
4. **Context 预算先于生成**、且可审计（Trace/Inspector），把"Token 浪费"当作一等问题处理。
5. **明确 Non-goals 与第一阶段禁止事项**（不引入独立向量库、不引入云 Backend、不新增无限 Entity Type/Predicate），有效防范围蔓延。
6. **Rule 9/10（IDs cheaper than payloads / References cheaper than repeated context）** 具备可执行的落地形态，不是空泛原则。

## 10. 风险与设计缺口

### 10.1 落地阻塞级（需先补齐再写代码）

| # | 问题 | 影响 |
|---|---|---|
| G1 | **枚举缺失**：`ClaimStatus / EntityStatus / ReviewStatus / RelationStatus / Polarity / Modality / ClaimType / EvidenceLevel / SourceType` 只出现名字，无取值列表 | 无法定义 Rust enum，无法建表约束 |
| G2 | **两份文档顺序冲突**：Entity Resolution PRD 为 `Exact→Alias→Normalized→Fuzzy→Semantic`，TDD 为 `Exact→Normalized→Alias→Fuzzy→Semantic Candidate` | 行为不确定、测试无法断言 |
| G3 | **supersedes 方向未定义**：`claim_relations(source_claim, target_claim)` 谁是旧、谁是新未写明；TDD 第 12 节 SQL 用 `target_claim = claims.id AND relation='superseded'`，与枚举 `Supersedes` 命名不一致 | 直接决定 `get_current_claims()` 正确性 |
| G4 | **Temporal 未进入 Current 查询**：文档称 Current 由 status + evolution + temporal 派生，但示例 SQL 只判断 `status='verified'` 与 superseded 存在性 | "历史正确 ≠ 当前正确"这一核心卖点会失效 |
| G5 | **`relations` 与 `claim_relations` 边界模糊**：PRD 强调 Relation 与 Claim 不混淆，TDD 表清单两者并存，缺明确语义与不变量 | 图查询结果不可预期 |
| G6 | **Predicate 结构体缺字段**：PRD 要求 `conflict_rules / normalization_rules`，TDD 的 `struct Predicate` 未包含 | Conflict Engine 缺少规则输入 |
| G7 | **无 Claim 指纹定义**：duplicate 判定依赖同一性，但只有 `content_hash/source_hash/proposal_id/operation_id` | duplicate 与 coexists 无法稳定区分 |
| G8 | **缺少唯一索引/幂等键的 DDL 设计**：幂等是原则，但没落到约束 | 重复导入会产生脏数据 |

### 10.2 工程风险

| # | 风险 | 说明 |
|---|---|---|
| R1 | **范围过大** | 43 任务 / 8 Phase，且 P0 同时包含 Hybrid Search + Evolution Engine + Review，最小可用切片仍偏重 |
| R2 | **无 AI 时的降级路径未定义** | Local-first 承诺"无 API Key 可 Capture/CRUD"，但没有 API Key 时如何生成 Candidate Claim？是否支持纯手动录入？文档未写 |
| R3 | **Evolution 误报噪音** | 误判 supersedes/contradicts 会持续堆积 Review 队列；缺相似度阈值、静默策略、"批量接受"与误报回收机制 |
| R4 | **SQLite 向量规模上限未知** | float32 blob 全表 cosine 在 10 万级 chunk 下的延迟未评估，与 "Search <100ms" 目标可能冲突 |
| R5 | **迁移输入缺失** | Phase 8 依赖存量库的真实 schema 与样例库，但仓库内没有 schema 快照、迁移映射样例或数据 fixture |
| R6 | **版本化对象过多** | prompt/skill/reference/ontology/schema/history/task_packet 七类版本都要管理，`*_version` 的生成规则未定义 |
| R7 | **事件枚举不统一** | TDD 第 53 节 `AppEvent`（AgentStarted…）与第 84 节事件名（KnowledgeCommitted…）是两套，需合并为单一枚举 |
| R8 | **运行时依赖未验证** | Tauri 2 与 AgentScope Rust 的版本兼容、AG-UI adapter 的具体 crate/版本未指定 |
| R9 | **UI 信息架构未定** | Knowledge 首页默认视图是什么（列表 / Timeline / 最近变更）未定义；只有局部 UI 线框，无交互与空态/错误态设计 |
| R10 | **时间语义未定义** | `DateTime` 未说明 UTC/本地、精度（秒/毫秒），跨时区与 temporal overlap 判定会出偏差 |
| R11 | **归档/软删除语义缺失** | `archived` 出现在 Inbox 与 Idea/Question 状态，但 Claim/Entity 是否可归档、归档后是否参与检索未定义 |
| R12 | **性能指标缺规模前提** | "Graph Query <200ms" 未给出节点/边规模基线，无法验收 |
| R13 | **安全实现路径** | OS Secure Storage 需跨平台抽象（macOS Keychain / Windows Credential Manager / Linux Secret Service），文档只给了目标未给方案 |

## 12. 总评

设计思想层面这是**成熟度很高的规格**：核心不变量（不覆盖历史、证据一等、当前态派生、Context 预算前置）都找到了对应的结构性实现手段，而不是停留在口号；分层与依赖规则清晰，禁止事项明确，可测试点也已列出。

主要短板集中在**"从规格到代码"的最后一公里**：关键枚举、关系方向、Current 查询语义、幂等约束这些"必须唯一确定"的元素尚未闭合，且范围偏大、迁移输入缺失。

结论：**先闭合 G1–G8 这批语义空洞，然后用最小垂直切片验证 Evolution 闭环，再横向铺开** —— 这是当前性价比最高的推进方式。

新增发现的关键事实（原分析未覆盖）：
- 参考实现有**两套独立谓词注册表**（Claim 46 个 / Relation 19 个），同名谓词（如 `uses`）在两边的归属由归一化规则裁决，而不是靠约定。
- FTS5 使用 `tokenize='trigram'`——`unicode61` 会导致中文几乎无法检索，这是踩坑后的修正结论，wiki-ya 必须沿用。
- `semantic` 检索已存在"无 API Key 则降级为纯词法"的实现，**原报告 R2 风险实际已被参考实现回答**。
- RRF 参数确认为 `k = 60`。
- 参考实现中 `supersedes` **刻意不由确定性规则推断**，只接受 LLM 建议或人工判断——与 PRD「AI 提议、用户决定」完全一致。

剩余待裁决 8 项（D1–D8）已列入 `docs/领域枚举与不变量定义.md`，其中 D1（`supplements` vs `unclear`）、D2（时间字段来源）、D5（Evidence 层级命名）需要产品决策，其余可由工程直接定。
