## 3. ⚠️ 需要你裁决的语义分歧（未擅自改动）

### D-1：Claim 状态词表 —— `active` vs 现有 6 值模型

- **契约 §5**：`candidate / active / superseded / rejected`（4 值）。
- **实现**：`draft / candidate / verified / rejected / archived / superseded`（6 值，来自参考实现与 `docs/领域枚举与不变量定义.md`）。
- 映射：契约的 `active` ≈ 实现的 `verified`；实现另有 `draft`、`archived`。

**影响面**：若按契约改名为 `active`，会动到 DB `CHECK` 约束、`ClaimStatus` 枚举、约 40+ 处测试断言、前端状态标签，以及 `docs/领域枚举与不变量定义.md`。

**我的建议（未执行）**：保留 6 值模型（信息量更大、与既有文档/测试一致），在契约中补一条「`active` ≡ 实现的 `verified`」映射。若你要求字面统一，我再做一次性重命名 + 迁移。

### D-2：`candidate` 算不算 Current —— 语义冲突

- **契约 §5.1/§16**：`candidate` 需 `accept` 后才是 Current（即 **candidate 不是 Current**）。
- **实现**：`ClaimStatus::counts_as_current()` = `verified | candidate` → **candidate 被视为当前知识**。

**这是产品语义级差异，不是 bug**：实现的取向是 local-first「不因为没人工确认就把知识排除出当前视图」；契约的取向是「未经确认不得进入 Current」。

**影响面**：若按契约收紧，所有手工/抽取产生的 `candidate` 将不再出现在 Current 检索/上下文里，直到被 Review 接受——显著改变 Search / Ask 召回与大量测试预期。

**我的建议（未执行）**：需你明确取向；若采用契约语义，建议同时提供「批量确认」入口，避免用户知识被大量挡在 Current 之外。
