# wiki-ya Knowledge Contract & Evolution Specification

**Version:** 1.0
**Status:** Draft for Implementation
**Scope:** Claim / Evidence / Current Knowledge / Evolution / Temporal Semantics / Review / Rollback
**Goal:** 建立 wiki-ya 的知识语义契约，确保知识长期积累后仍然正确、可解释、可追溯。

---

# 1. 文档目的

wiki-ya 的核心价值不是“存储很多笔记”，而是：

> **让知识在持续进入、变化和被查询的过程中保持可信。**

因此，本规范定义：

1. 什么是 Knowledge
2. 什么是 Claim
3. 什么是 Evidence
4. 什么叫 Current Knowledge
5. 什么情况下一个知识会取代另一个知识
6. 什么情况下两个知识可以同时存在
7. 什么情况下两个知识只是冲突，但不能改变 Current
8. 时间字段分别代表什么
9. Review 如何改变知识状态
10. Rollback 如何恢复知识状态
11. AI 在整个流程中拥有什么权限
12. Domain / Application / Infrastructure 分别负责什么

本规范优先级高于具体 UI 实现。

---

# 2. 核心原则

wiki-ya 必须遵守以下原则。

## 2.1 Knowledge is append-first

知识变化优先表现为：

```text
New Claim
+
New Evidence
+
Evolution Relation
```

而不是：

```text
UPDATE old_claim
```

旧知识默认保留。

---

## 2.2 AI proposes, Domain decides

AI 可以：

```text
Extract
Suggest
Compare
Rank
Explain
```

AI 不直接拥有：

```text
Delete knowledge
Supersede knowledge
Change current state
```

最终状态必须经过 Application + Domain。

---

## 2.3 Current Knowledge is derived

Current Knowledge 不是：

```text
latest claim
```

也不是：

```text
highest confidence claim
```

而是一个由：

```text
Claim State
+
Accepted Evolution
+
Temporal Semantics
```

共同决定的结果。

---

## 2.4 History must not be destroyed

当新知识取代旧知识时：

```text
old claim
```

不能删除。

应该保留：

```text
old claim
+
new claim
+
supersedes relation
+
review decision
```

这样可以回答：

> 为什么现在是这个知识？

也可以回答：

> 以前系统认为是什么？

---

## 2.5 Conflict is not truth

两个 Claim 冲突时：

```text
contradicts
```

不代表：

```text
new = correct
```

只有经过明确的 Evolution Decision：

```text
accept supersession
```

旧知识才可以离开 Current State。

---

# 3. 核心领域模型

wiki-ya 的最小知识模型：

```text
Source
   ↓
Evidence
   ↓
Claim
   ↓
Evolution
   ↓
Current Knowledge
```

其中：

### Source

原始资料。

例如：

```text
Document
Web Page
GitHub Repository
Imported File
Manual Input
```

---

### Evidence

从 Source 中支持某个 Claim 的具体依据。

例如：

```text
Document: package.json
Snippet: "react": "^19.0.0"
```

Evidence 本身不是 Knowledge。

---

### Claim

系统认为“可能成立”的一个知识陈述。

例如：

```text
wiki-ya uses React 19
```

Claim 可以：

```text
active
superseded
rejected
```

---

### Evolution

两个 Claim 之间发生的语义关系。

例如：

```text
Claim A → Claim B
```

关系可以是：

```text
duplicate
coexists
supplements
supersedes
contradicts
unclear
```

Evolution 是：

> **知识变化本身的记录。**

---

### Current Knowledge

当前被系统认可为有效的 Claim 集合。

它是派生概念，而不是独立事实来源。

---

# 4. Claim Contract

## 4.1 Claim 基本结构

推荐逻辑结构：

```rust
struct Claim {
    id: ClaimId,

    subject: EntityId,

    predicate: Predicate,

    object: ClaimObject,

    polarity: Polarity,

    status: ClaimStatus,

    recorded_at: DateTime,

    observed_at: Option<DateTime>,

    valid_from: Option<DateTime>,

    valid_until: Option<DateTime>,
}
```

其中：

```text
subject
predicate
object
polarity
```

共同表达 Claim 的语义。

---

# 5. Claim Status

Claim 只允许以下生命周期：

```text
candidate
active
superseded
rejected
```

推荐生命周期：

```text
candidate
    │
    ├──── reject ────→ rejected
    │
    └──── accept ────→ active
                           │
                           └── superseded ───→ superseded
```

---

## 5.1 candidate

表示：

> 系统发现了一个可能成立的新知识，但尚未获得最终认可。

来源可能包括：

```text
AI Extraction
Manual Claim
Imported Knowledge
Evolution Proposal
```

---

## 5.2 active

表示：

> 当前知识状态中认可的 Claim。

但：

> active 不意味着永远正确。

未来可能被：

```text
superseded
```

---

## 5.3 superseded

表示：

> 该 Claim 曾经成立/被认可，但后来已经被一个明确接受的新 Claim 取代。

superseded Claim 必须继续保留。

---

## 5.4 rejected

表示：

> 该 Claim 被明确认为不应进入当前知识。

rejected 不应该作为 Current Knowledge。

---

# 6. Evidence Contract

Evidence 用于回答：

> 为什么系统相信这个 Claim？

结构建议：

```rust
struct Evidence {
    id: EvidenceId,

    source_id: SourceId,

    locator: EvidenceLocator,

    excerpt: Option<String>,

    observed_at: Option<DateTime>,
}
```

---

## 6.1 Evidence 不等于 Claim

例如原文：

```text
"wiki-ya uses React 19."
```

Evidence 是：

```text
Source: package.json
Snippet: react = 19.x
```

Claim 是：

```text
wiki-ya uses React 19
```

系统可以从一个 Evidence 推导多个 Claim。

也可以一个 Claim 由多个 Evidence 支持。

关系：

```text
Evidence 1 ──┐
Evidence 2 ──┼──→ Claim
Evidence 3 ──┘
```

---

# 7. Evidence 信任原则

Evidence 本身不自动决定 Claim 正确。

推荐逻辑：

```text
Evidence
   ↓
supports Claim
```

而不是：

```text
Evidence
   ↓
Claim = true
```

因为：

```text
旧文档
错误文档
过时网页
用户错误输入
```

都可能成为 Evidence。

最终是否成为 Current Knowledge，仍然由 Claim + Evolution 决定。

---

# 8. Evolution Contract

Evolution 表示：

> 两个 Claim 之间存在明确的语义关系。

核心结构：

```rust
struct ClaimRelation {
    id: RelationId,

    source_claim: ClaimId,

    target_claim: ClaimId,

    relation: ClaimRelationType,

    confidence: f32,

    status: ClaimRelationStatus,

    reason: Option<ComparisonReason>,

    reviewed_at: Option<DateTime>,
}
```

---

# 9. Relation Semantics

## 9.1 duplicate

语义：

> 两个 Claim 表达基本相同的事实。

例如：

```text
A: wiki-ya uses React 19
B: wiki-ya is built with React 19
```

结果：

```text
A active
B candidate/rejected
```

duplicate 不产生知识变化。

推荐：

```text
relation.status = accepted
```

但：

> 不应该因为 duplicate 直接修改 Current Knowledge。

---

# 10. coexists

语义：

> 两个 Claim 不应该互相取代，可以同时成立。

例如：

```text
A:
legacy-service uses React 18

B:
wiki-ya uses React 19
```

即使它们 predicate 相同：

```text
uses_version
```

只要 subject/context 不同，就可能 coexists。

结果：

```text
A active
B active
```

---

# 11. supplements

语义：

> B 没有否定 A，而是提供额外信息。

例如：

```text
A:
wiki-ya uses React 19

B:
wiki-ya uses React 19 and Vite 7
```

B 不应简单 supersede A。

两个 Claim 可以保持有效。

---

# 12. contradicts

语义：

> 两个 Claim 在同一语义范围内表达相互冲突的内容。

例如：

```text
A:
wiki-ya uses React 18

B:
wiki-ya uses React 19
```

结果：

```text
A active
B candidate
```

不能自动：

```text
A → superseded
```

因为：

```text
contradiction ≠ truth decision
```

---

# 13. supersedes

语义：

> 新 Claim 已经被明确认可，可以取代旧 Claim 在当前知识中的地位。

这是整个系统中最特殊的 Relation。

只有：

```text
accepted supersedes
```

才能改变 Current Knowledge。

例如：

```text
A:
wiki-ya uses React 18

B:
wiki-ya uses React 19
```

Review：

```text
Accept change
```

产生：

```text
B active
A superseded
```

并留下：

```text
B --supersedes--> A
```

---

# 14. unclear

语义：

> 系统无法可靠判断两个 Claim 的关系。

此时：

> 不应该强行产生业务关系。

允许：

```text
candidate
```

但不能因为 unclear 自动改变 Current。

---

# 15. Evolution Decision Contract

用户 Review 的实际选择不应该直接暴露底层 Relation。

用户层面只需要：

```text
Accept change
Keep both
Reject
```

内部映射：

```text
Accept change
    ↓
accepted supersedes

Keep both
    ↓
accepted coexists

Reject
    ↓
rejected proposal
```

---

# 16. Current Knowledge Contract

Current Knowledge 定义：

> 在当前知识状态下，系统认可为有效且未被 accepted supersedes 取代的 Claim。

可表达为：

```text
CurrentClaim =
    status == active
    AND
    not superseded_by_accepted_evolution
```

更完整地：

```text
Current Knowledge
=
Active Claim
-
Claims superseded by accepted Evolution
+
Temporal validity
```

---

# 17. 严格禁止的 Current 推导方式

以下方式禁止作为唯一规则。

## 17.1 禁止按照 created_at 选择

错误：

```sql
ORDER BY created_at DESC
LIMIT 1
```

因为：

> 最新记录不一定是最新事实。

---

## 17.2 禁止按照 confidence 选择

错误：

```text
highest confidence = current
```

因为：

> confidence 是判断信号，不是业务真相。

---

## 17.3 禁止按照 embedding similarity 选择

错误：

```text
top semantic match = current
```

Retrieval relevance：

> 不等于 knowledge validity。

---

# 18. Temporal Semantics

时间是 wiki-ya 最容易出现隐性错误的地方。

必须严格区分：

```text
recorded_at
observed_at
valid_from
valid_until
```

---

# 19. recorded_at

含义：

> wiki-ya 什么时候记录这个 Claim。

例如：

```text
2026-09-13 15:30
```

这是系统时间。

它不是事实本身发生的时间。

---

# 20. observed_at

含义：

> Evidence / Source 在什么时候观察到这个事实。

例如：

```text
GitHub commit date
Article published date
Document date
```

如果来源没有明确时间：

```text
NULL
```

不要猜。

---

# 21. valid_from

含义：

> 这个事实从什么时候开始成立。

例如：

```text
React 19 became the project's version
```

可以有：

```text
valid_from = 2026-08-20
```

但只有来源明确支持时才能写入。

---

# 22. valid_until

含义：

> 这个事实在什么时候结束有效。

不要因为：

```text
newer claim exists
```

就自动推断：

```text
valid_until = new_claim.recorded_at
```

推荐由：

```text
accepted supersedes
```

或明确来源时间推导。

---

# 23. Temporal Unknown

如果无法确定：

```text
valid_from = NULL
valid_until = NULL
```

这不是错误。

它表示：

> 系统知道这个 Claim，但不知道它准确的事实时间边界。

---

# 24. Current + Temporal

一个 Claim 可以：

```text
status = active
```

但不代表它永远有效。

例如：

```text
valid_from = 2025-01-01
valid_until = 2025-12-31
```

则：

```text
status = active
```

仍可能不是：

```text
Current for 2026
```

因此最终的 Current 查询必须同时考虑：

```text
Claim Status
+
Accepted Evolution
+
Temporal Window
```

---

# 25. Review Contract

所有可能改变 Current Knowledge 的操作必须通过 Review。

Review 需要回答：

```text
What changed?
Why?
Evidence?
Impact?
```

---

# 26. Review Decision

```rust
enum ReviewDecision {
    Accept,
    KeepBoth,
    Reject,
}
```

Application 层负责：

```text
validate
authorize
transaction
domain transition
persist
```

Domain 层负责：

```text
relation semantics
state transition
invariants
```

---

# 27. Review Transaction

一次 Accept 必须是单事务：

```text
BEGIN

1. Validate relation

2. Validate source claim

3. Validate target claim

4. Update relation status

5. Apply evolution state transition

6. Update affected claim state

7. Persist audit information

COMMIT
```

任何失败：

```text
ROLLBACK
```

---

# 28. Review Invariants

## Invariant A

Reject candidate：

```text
Current Knowledge 不改变。
```

---

## Invariant B

Keep Both：

```text
双方都保持 active
```

前提：

> Domain 判断该决策合法。

---

## Invariant C

Accept supersedes：

```text
source → active
target → superseded
relation → accepted
```

---

## Invariant D

Accept duplicate：

```text
不会无理由把 active Claim 改成 superseded。
```

---

# 29. Rollback Contract

Rollback 的意义：

> **撤销一次 Evolution Decision，而不是删除历史。**

例如：

```text
A active

B candidate

Accept supersedes

A superseded
B active
```

Rollback：

```text
A active
B restored to previous status
```

同时保留：

```text
original evolution
review event
rollback event
```

---

# 30. Rollback 禁止事项

不能：

```sql
DELETE evolution
```

不能：

```sql
DELETE claim
```

不能：

```sql
UPDATE claim SET status = ...
```

作为唯一业务逻辑。

必须由：

```text
EvolutionService.rollback(...)
```

执行。

---

# 31. AI 权限边界

AI 可以执行：

```text
Extraction
Comparison
Classification
Summarization
Ranking
Explanation
```

AI 不可以直接执行：

```text
accept supersedes
reject claim
delete claim
change current
```

正确：

```text
AI
 ↓
Proposal
 ↓
Application
 ↓
Domain
 ↓
Human Review
 ↓
Persist
```

# 32. Extraction Contract

AI Extraction 的输出应该是：

```rust
struct ClaimCandidate {
    subject: ...
    predicate: ...
    object: ...
    evidence: ...
}
```

不是直接产生：

```text
active Claim
```

流程：

```text
Document
 ↓
Chunk
 ↓
AI Extraction
 ↓
Candidate Claims
 ↓
Validation
 ↓
Normalization
 ↓
Entity Resolution
 ↓
Existing Claim Comparison
 ↓
Evolution Proposal
 ↓
Review
 ↓
Persist
```

---

# 33. 大文档 Extraction

禁止长期依赖：

```text
entire document
 ↓
one giant prompt
 ↓
one response
```

应使用：

```text
Document
 ↓
Chunks
 ↓
Token Budget
 ↓
Batch Extraction
 ↓
Candidate Merge
 ↓
Dedup
 ↓
Evolution
```

Batch 失败：

> 只重试失败 Batch。

不能因为单 Batch 失败而破坏其它结果。

---

# 34. Search Contract

Search 只回答：

> “哪些 Knowledge / Evidence / Source 与我的查询相关？”

Search 不负责修改 Knowledge。

其数据来源应统一经过：

```text
RetrievalService
```

---

# 35. Ask Contract

Ask 流程：

```text
Question
 ↓
Retrieval
 ↓
Context Compilation
 ↓
LLM
 ↓
Answer
 ↓
Citation
```

Ask 不应该自己建立第二套知识状态。

---

# 36. Citation Contract

回答中的引用必须能够追溯到：

```text
Answer
 ↓
Claim
 ↓
Evidence
 ↓
Source
```

理想结构：

```text
[1]
 ↓
Claim #123
 ↓
Evidence #44
 ↓
package.json
```

而不是：

```text
Answer
 ↓
some document
```

---

# 37. Retrieval Contract

Retrieval 可以组合：

```text
Lexical
Semantic
Entity
Claim
Temporal
Evolution
```

但 Retrieval Score 只用于：

> 排序。

不能用于：

> 修改 Knowledge State。

即：

```text
score = relevance
```

不是：

```text
score = truth
```


# 40. Evolution Review UI Contract

用户看到的是：

```text
Before
After
Why
Evidence
Decision
```

而不是：

```text

```

底层信息可以存在 Advanced Details。

# 41. Auditability

每次改变 Current Knowledge 的行为都必须能够追溯：

```text
Who
When
What
Why
Based on which evidence
Which relation
Previous state
New state
```

至少应该知道：

```text
claim_id
relation_id
review_decision
timestamp
previous_status
new_status
```

---

# 42. Domain Invariants

Domain 必须保证：

### I-001

`rejected` Claim 不得成为 Current Knowledge。

### I-002

只有 accepted `supersedes` 才能产生 `superseded` 状态。

### I-003

`contradicts` 不自动导致 supersession。

### I-004

`coexists` 不自动导致 supersession。

### I-005

删除 Claim 不是正常 Evolution 操作。

### I-006

Evolution Relation 的 source / target 方向必须稳定：

```text
source = newer / proposing Claim
target = existing Claim
```

### I-007

Rollback 必须保留历史事件。

### I-008

Current Knowledge 不得仅基于 timestamp、confidence 或 retrieval score 决定。

# 48. 数据库原则

数据库应该存：

```text
facts
relations
evidence
history
```

数据库不应该成为：

```text
business logic engine
```

尤其禁止将以下语义散落在 SQL：

```text
if claim.status == ...
if relation == ...
if newer ...
```

这些应该属于 Domain。

## 49.3 E2E Tests

### Contradiction

```text
A active
B candidate

→ contradicts

Current 不变
```

### Supersession

```text
A active
B candidate

Accept

→ A superseded
→ B active
```

### Keep Both

```text
A active
B active
```

### Reject

```text
A active
B rejected
```

### Rollback

```text
B active
A superseded

Rollback

→ A active
```

# 50. Contract Test Matrix

| 场景      | Relation    | Review   | Current 变化 |
| ------- | ----------- | -------- | ---------- |
| 完全相同    | duplicate   | Accept   | 否          |
| 可以同时成立  | coexists    | Accept   | 否          |
| 补充信息    | supplements | Accept   | 通常否        |
| 信息冲突    | contradicts | Pending  | 否          |
| 明确替代    | supersedes  | Accept   | 是          |
| 无法判断    | unclear     | Pending  | 否          |
| 新知识被拒绝  | any         | Reject   | 否          |
| 已接受变更撤销 | supersedes  | Rollback | 恢复         |

# 51. 最关键的 E2E Scenario

这个场景必须长期存在：

```text
Document A
    ↓
Claim A
    ↓
active

Document B
    ↓
Claim B
    ↓
compare(A, B)
    ↓
supersedes candidate
    ↓
Review
    ↓
Accept
    ↓
A = superseded
B = active
    ↓
Ask
    ↓
Answer uses B

Rollback
    ↓
A = active
B = restored
    ↓
Ask
    ↓
Answer uses A
```

这一个测试实际上验证了整个产品最核心的价值链。

# 52. 不变量失败时怎么办

任何违反 Knowledge Contract 的情况：

```text
必须失败
```

而不是：

```text
尽可能继续运行
```

例如：

```text
accepted supersedes
但 target claim 不存在
```

应该：

```text
transaction rollback
```

而不是：

```text
relation 先保存下来
```

```text
 ↓
```

# 58. 禁止事项

未来开发中，以下方向默认禁止，除非证明当前 Contract 无法满足需求。

## 禁止 1

为了“看起来智能”自动 supersede Claim。

---

## 禁止 2

因为新 Claim 的 timestamp 更新就覆盖旧 Claim。

---

## 禁止 3

因为 AI confidence 高就自动修改 Current。

---

## 禁止 4

为了搜索效果直接修改 Claim 状态。

---

## 禁止 5

让 Retrieval Score 成为 Knowledge Truth。

---

## 禁止 6

让 UI 直接修改 Claim Status。

---

## 禁止 7

让 AI Agent 直接执行 Knowledge Mutation。

## 禁止 8

用删除旧 Claim 的方式表达知识演化。

# 60. 最终产品模型

当用户使用 wiki-ya 时，他不需要理解复杂架构。

他的心智模型应该只有：

```text
我记录了一些东西
        ↓
系统提取出知识
        ↓
我确认
        ↓
知识进入当前状态
        ↓
以后发现新信息
        ↓
系统告诉我发生了什么变化
        ↓
我决定是否接受
        ↓
历史保留下来
```

这就是 wiki-ya 真正应该实现的体验。

---

# 61. 最终原则

wiki-ya 的核心不是：

> **AI 帮我生成更多知识。**

而是：

> **AI 帮我整理知识，而系统保证知识变化是可解释、可追溯、可逆的。**

因此整个系统的核心循环应该是：

```text
Evidence
   ↓
Claim
   ↓
Review
   ↓
Current Knowledge
   ↓
New Evidence
   ↓
Evolution
   ↓
Review
   ↓
New Current Knowledge
```

而不是：

```text
Document
 ↓
LLM
 ↓
Database
```

# 62. 一句话 Contract

如果未来所有设计都需要压缩成一句话：

> **New information may propose a change, but only an explicit and valid Evolution decision may change Current Knowledge.**

中文：

> **新信息只能提出知识变化，只有经过合法演化决策，才能改变当前知识。**

这句话应该成为 wiki-ya 后续 Domain、Application、AI 和 UI 设计的最高原则。
