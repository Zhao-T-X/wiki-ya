- 默认值：`Resource`（人工创建时）。
- **禁止 LLM 自由创造**（PRD §10）：抽取 schema 的 `enum` 与此列表必须同源。

## 1.2 ClaimPredicate（46，封闭集合）✅

```

uses, retrieves, accesses, provides, receives, generates, produces, creates, extracts, transforms,
supports, enables, allows, improves, reduces, increases, decreases, prevents, causes, leads_to,
```

- 归一化：小写 + 非字母数字转 `_` + 折叠连续 `_` + 去首尾 `_`（`normalize_predicate`）。
- Schema 约束：`^[a-z][a-z0-9_]*$`。

## 1.4 RelationNormalizationRules（Claim ↔ Relation 的边界由它强制）✅

这条规则集**就是 PRD §13「Relation 与 Claim 不混淆」的实现手段**：

```
outcomes                     = DIRECT_RELATION | CONDITIONAL_RELATION | CLAIM_ONLY | REJECTED

direct_relation_requirements = subject_resolves_to_entity, object_resolves_to_entity,
                               predicate_in_relation_registry, explicit_canonical_semantics,
                               positive_polarity, asserted_modality, no_material_unresolved_condition,
                               valid_direct_evidence, long_term_graph_value, source_target_types_allowed

claim_only_predicates        = retrieves, provides, receives, generates, produces, extracts, supports,
                               enables, causes, leads_to, improves, reduces, increases, decreases,
                               prevents, addresses, better_than, worse_than, similar_to, different_from

always_claim_only_predicates = better_than, worse_than, similar_to, different_from, improves,
                               addresses, supports, causes, leads_to, retrieves, provides, receives,
                               generates, produces, extracts, reduces, increases, decreases, prevents

context_sensitive_predicates = uses, develops, creates, maintains, owns, studies, evaluates,
                               applied_to, designed_for, compares_with

never_semantically_upgrade   = (uses→depends_on), (designed_for→improves),
                               (based_on→derived_from), (compares_with→better_than)
```

要点：
- `direct_relation_requirements` 全部满足才可写 `relations` 表；缺任一 → 降级为 `Claim`。
- `always_claim_only_predicates` 是硬红线，**即使谓词同名存在于 Relation 注册表也必须走 Claim**（如 `uses` 在两边都存在）。
- `never_semantically_upgrade` 防止 LLM 把弱语义升级成强语义。
- ➕ wiki-ya 需新增枚举：`NormalizationOutcome`（4 值）。

## 1.5 注册表版本 ✅

`registry_version()` = 对 `schemas/` 下**所有 JSON 文件的文件名 + 字节内容**做 SHA-1，截取前 12 位十六进制。

- 任一注册表/抽取 schema 改动 → 指纹变化 → 所有 Context Cache Key 变化 → **无需手工失效**（PRD §38 的实现）。
- ➕ wiki-ya 需将其纳入 TDD §44 的 `Cache Key` 组合哈希。

# 2. Claim 域枚举

## 2.1 ClaimStatus（6）✅

```
draft | candidate | verified | rejected | archived | superseded
```

- 默认 `candidate`（LLM 产出）；人工录入默认 `candidate`。
- **`superseded` 与 `rejected` 必须区分**：前者是历史，后者是错误。这个区分是检索层"优先当前知识、但仍能回答历史问题"的前提。
- 非法值必须被数据库 CHECK 拒绝（参考实现有对应测试断言）。

## 2.2 ClaimType（8）+ 别名 ✅

```
factual | definitional | causal | comparative | evaluative | predictive | normative | hypothetical
```

| 别名 | 归一为 | | 别名 | 归一为 |
|---|---|---|---|---|
| fact | factual | | comparison | comparative |
| definition | definitional | | evaluation | evaluative |
| cause / causation / causality | causal | | prediction | predictive |
| hypothesis | hypothetical | | norm | normative |

默认 `factual`。

## 2.3 Polarity（2）+ 别名 ✅

```
positive | negative
```
别名：`affirmative/true/yes → positive`，`negated/false/no → negative`。默认 `positive`。

## 2.4 Modality（6）+ 别名 ✅

```
asserted | possible | probable | capable | necessary | recommended
```

| 别名 | 归一为 |
|---|---|
| actual / definite / certain | asserted |
| maybe | possible |
| likely / probably | probable |
| can / able | capable |
| must / required | necessary |
| should | recommended |

默认 `asserted`。

> PRD §31 提到 `Conditional` 概念（`CONDITIONAL_MODALITIES = {conditional, possible, probable}`），但 `conditional` **不在** Modality 枚举内，它由 `context` 承载。⚠️ 见 D3。

## 2.5 Confidence ✅

`f32`，区间 `[0,1]`，未知用 NULL（SQL `CHECK(confidence IS NULL OR confidence BETWEEN 0 AND 1)`）。

## 2.6 ClaimObject（5）✅

```
Entity(EntityId) | Literal(String) | Number(f64) | Boolean(bool) | Date(DateTime)
```
存储侧对应 `object_id`（可空）与 `object_text`（可空）两列；可比性以 `object_id` 优先，退化为 `object_text` 的 casefold 文本。

## 2.7 FunctionalPredicate（单值谓词，3）✅

```
is | defined_as | classified_as
```

语义：**同一 subject 只能有一个值**。两个不同 object 出现时 → 视作"知识变更"而非"两条并存事实" → 判为 `contradicts` 并进入 Review（置信度 0.55）。
设计意图（参考实现原话）：**故意保守、故意小**。不在集合内的谓词一律退化为 `coexists`（不破坏任何东西，也不制造伪冲突）。**扩展靠证据，不靠猜测。**

# 4. 演化与审核

## 4.1 ClaimRelationType ⚠️

| 来源 | 取值 |
|---|---|
| PRD §19 / TDD §10 | duplicate, coexists, **supplements**, supersedes, contradicts（5） |
| 参考实现 `claim_relations.py` + DB CHECK | duplicate, coexists, supersedes, contradicts, **unclear**（5） |

差异：PRD 有 `supplements`，参考实现有 `unclear`。见 **D1**。

## 4.2 ClaimRelationStatus（3）✅

```
candidate | accepted | rejected
```
默认 `candidate`。`accepted` 才产生事实效果。

## 4.3 判定优先级（Review 队列排序）✅

```
duplicate(0) < supersedes(1) < contradicts(2) < coexists(3) < unclear(4)
```
同优先级按 confidence 降序。

## 4.4 确定性判定表（`compare_claim`）✅ —— 实现 G3 的直接答案

前置：`same_subject && same_predicate`，否则直接 `unclear`（confidence 0.0，action=ignore）。

| 条件 | 结论 | confidence | suggested_action | 是否自动 accepted |
|---|---|---|---|---|
| object 相同 且 polarity 相同 | duplicate | 0.97 | link_evidence | ✅ 自动 accepted |
| object 相同 且 polarity 不同 | contradicts | 0.90 | review | ❌ 人工 |
| object 不同 且 predicate ∈ Functional | contradicts | 0.55 | review | ❌ 人工 |
| object 不同 且 predicate ∉ Functional | coexists | 0.70 | keep_both | ✅ 自动 accepted |
| 任一侧 object 无法解析 | unclear | 0.20 | review | ❌ 不写入 |

**关键规则：`supersedes` 永不由确定性规则推断。** 它需要时间或文本证据（"某某已取代某某"），只能来自 LLM 建议或人工判断。参考实现原话：*False certainty is worse than an honest question.*

## 4.5 方向约定 ✅ —— 实现 G3

```rust
struct ClaimRelation {
    source_claim_id: ClaimId,   // 新 claim（发起方）
    target_claim_id: ClaimId,   // 旧 claim（被影响方）
    target_previous_status: Option<ClaimStatus>,  // 旧 claim 被取代前的状态，用于精确回滚
}
```

- `supersedes` 语义：**source 取代 target**，即 `source_claim` 是新的。
- 约束：`UNIQUE(source_claim_id, target_claim_id, relationship)`，且写入前检查反向是否已存在 → **同一对 claim 只留一行**，避免双向重复上报。
- 任何方向歧义都以该约定为准；PRD/TDD 中的 `relation='superseded'` 写法（TDD §12）**是笔误，应改为 `relationship='supersedes'`**。

## 4.6 状态迁移（唯一入口）✅

```
PATCH claim_relation { status: accepted, relationship: supersedes }
    → 记录 target_previous_status = 旧 claim 当前状态
    → UPDATE claims SET status='superseded' WHERE id = target_claim_id

PATCH claim_relation { status: candidate }（从已确认状态回退）
    → UPDATE claims SET status=target_previous_status
       WHERE id = target_claim_id AND status='superseded'
```

不变量：
- 回滚**精确恢复**原状态，不是猜一个默认值（参考实现有测试断言）。
- CLAIM 的 `content / object_id / subject_id` 在任何演化中**不被修改**（测试断言 `object_id == 'o1'`、`content` 原样）。
- 只有 `supersedes` + `accepted` 才写 `superseded`；`contradicts` 不改变任何 claim 状态。

## 4.7 Current Knowledge 派生 ⚠️ —— 实现 G4

参考实现（无时间字段）：

```
covered = { (subject, predicate) | status != 'superseded' }
输出:
  status == 'superseded' 且 (subject,predicate) ∈ covered  → 丢弃（当前知识优先）
  status == 'superseded' 且 不在 covered                   → 保留并标记 lifecycle='superseded'
  其他                                                     → 原样保留
```

即：**历史从不删除**——"谁是现任 CEO"不会用被取代的陈述回答，但"谁是前任 CEO"仍有证据可答。

➕ wiki-ya 新增时间维度后，Current 判定应扩展为：

```
status != 'superseded'
AND NOT EXISTS (superseded 关系指向本 claim 且 relation.status = 'accepted')
AND (valid_from IS NULL OR valid_from <= now)
AND (valid_until IS NULL OR valid_until > now)
AND (status 属于「当前知识」集合，见 D2)
```

⚠️ 现有两文档未定义 `valid_from/valid_until` 的**数据来源**（抽取自文本时间？等于 `recorded_at`？），见 **D2**。

## 5.2 Document / Chunk 不变量 ✅

- `documents.content_hash` = SHA-256(content)，**UNIQUE** → 导入幂等的实现手段（PRD §70）。
- `chunks UNIQUE(document_id, chunk_index)`；`start_offset/end_offset` 指向原文，**Document 永不因结构化知识被改写**。
- Chunk 由 `document_id` CASCADE 删除，但 Document 本身不因 Claim 变化而改动。
- FTS5 使用 **`tokenize='trigram'`**（不是 `unicode61`）——`unicode61` 会把整段中文当一个 token，导致中文几乎搜不到；trigram 让中文和英文的子串匹配一致。⚠️ 这是从参考实现踩坑后修正的结论，**wiki-ya 必须沿用 trigram**。
- FTS 为 external-content 表（`content='documents'`, `content_rowid='rowid'`），靠 AFTER INSERT/DELETE/UPDATE 三个 trigger 同步。

```

PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;
```

## 6.5 EvidenceLevel ⚠️ —— 实现 PRD §18

| 来源 | 层 |
|---|---|
| PRD §18 | L1 Summary → L2 Claim → L3 Evidence → L4 Chunk → L5 Original Source |
| 参考实现（含实际渲染逻辑） | L1 quote → L2 quote+context → L3 paragraph → L4 chunk → L5 multi-chunk |
| 参考实现默认上限 | `DEFAULT_MAX_LEVEL = L4 (chunk)` |

参考实现的可运行语义（每层有真实渲染分支，字符上限 `{L1:400, L2:420, L3:800}`）：

```
L1 quote           命中引文本身
L2 quote+context   引文 + 单句窗口（默认回退层，触发条件见下）
L3 paragraph       包含引文的整段（空白分块）
L4 chunk           整个 chunk
L5 multi-chunk     多 chunk（默认不可达，需显式提升）
```

升层触发（只升不降，原因记录最严重的一条）：

| 触发 | 结果层 | 原因文案 |
|---|---|---|
| 无存储引文 | ≤ L3 | no stored quote — using the surrounding paragraph |
| 证据命中过少 | L2 | too few evidence hits to ground the answer |
| claim 为条件式 | ≥ L2 | conditional claim — the condition sits next to the quote |
| confidence < 0.6 | ≥ L2 | low confidence |
| 发现冲突证据 | ≥ L3 | conflicting evidence found for this question |

其他常量：`DEFAULT_PER_DOCUMENT_CAP = 2`、`SIMILAR_QUOTE_RATIO = 0.85`、`MIN_FUZZY_CHARS = 40`、`MAX_OTHER_CLAIMS = 2`。

见 **D5**：PRD 的层名与实现语义不一致，需二选一并统一文档。

| INV-04 | 别名在同一实体下唯一，不同实体可共享别名 | `PRIMARY KEY(entity_id, alias_normalized)` |
| INV-05 | Claim 不修改、不删除，只演进 | 无 DELETE claim 路径；演化只改 `status` |
| INV-06 | Claim 的 subject/predicate/object/content 在演化中不变 | 服务层 + 测试断言 |
| INV-07 | 同一 claim 对只存在一条 relation | `UNIQUE(source, target, relationship)` + 反向预检查 |
| INV-08 | 只有 `supersedes` + `accepted` 能产生 `superseded` | 单一入口 `update_claim_relation` |
| INV-09 | 取消 supersedes 必须精确恢复旧状态 | `target_previous_status` |
| INV-10 | `duplicate/coexists` 可自动 accepted；`contradicts/supersedes/unclear` 必须人工 | `suggested_action` 白名单 |
| INV-11 | `supersedes` 不由确定性规则推断 | `compare_claim` 中无该分支 |
| INV-12 | 一切状态值受枚举约束，非法值被拒绝 | DB `CHECK` + Rust enum + 校验函数抛错 |
| INV-13 | 谓词不得越出注册表 | `claim_predicate_allowed` / `relation_spec` 返回 None 即拒绝 |
| INV-14 | 关系两端类型必须匹配注册表（`*` 通配） | `relation_types_allowed` |
| INV-15 | Relation 只在 `direct_relation_requirements` 全满足时写入 | 归一化引擎 outcome = DIRECT_RELATION |
| INV-16 | `always_claim_only_predicates` 永不写入 relations | 归一化引擎硬规则 |
| INV-17 | 语义不得升级（`never_semantically_upgrade`） | 归一化引擎硬规则 |
| INV-18 | confidence 恒在 `[0,1]` 或 NULL | DB `CHECK` |
| INV-19 | Relation 与 Claim 在同一事务内提交 | Application 层事务边界（TDD §69） |
| INV-20 | 注册表版本变化自动使所有 Cache Key 失效 | `registry_version()` 入 Cache Key |
| INV-21 | 缓存失效永不阻塞执行 | 缓存读写异常吞掉，视为 miss |
| INV-22 | 派生数据可重建，原始数据不可丢 | TDD §85 分类 |
| INV-23 | Chunk 下标在文档内唯一连续 | `UNIQUE(document_id, chunk_index)` |
| INV-24 | FTS 与 documents 最终一致 | trigger 同步 + `rebuild` 修复路径 |
