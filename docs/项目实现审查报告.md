## 0. 总体结论

- **架构分层总体健康**：依赖方向基本遵守（UI → Commands → Application → Domain），事务边界在核心写路径（`create_document` / `create_claim` / `analyze_document` / `decide_relation`）基本正确，无 SQL 注入点（全部绑定参数）。
- **真正的问题集中在三类**：
  1. **AI 链路对"模型能力"做了错误假设**（这是你近期抽取失败的根因，见 §1）；
  2. **若干"规格声称强制、代码实际未强制"的不变量**（§2、§6）；
  3. **前后端契约漂移 + 可空字段被当成非空**（§5）。
- 存在**系统性文档/实现漂移**：README、IPC 契约、事件契约三处都与实现不一致（§6）。

## 1. AI 链路（你当前痛点的根因区）

### 1.1【高】抽取/问答假设模型是"非推理型"，推理模型直接失效
- **证据**：`ai/provider.rs` 全链路只认 `choices[].message.content`；本项目实测 `deepseek-flash` 会返回 `content:""` + `reasoning_content:"…"`，`finish_reason` 常为 `length`。
- **影响**：一切抽取/Ask 在推理模型上"看起来报错"，实质是**响应里根本没有正文**。当前已加的兜底（重试/流式/reasoning 抢救）只是补丁，仍脆弱。
- **建议**：
  - 在 Settings 明确标注"抽取/检索建议使用**非推理**模型（如 `deepseek-chat` / `gpt-4o-mini`）"；
  - 增加**模型能力探测**（首次调用记录 `finish_reason` 与 `content` 是否为空，落库为"该端点不支持非流式/为推理模型"的标记，后续自动走对应路径）；
  - 若坚持支持推理模型，则把"从 `reasoning_content` 提取 JSON"升级为一等公民（而非兜底）。

### 1.2【高】Ask 引用编号错位：上下文标 `[0]` 起，Sources 从 `1` 起
- **证据**：`application/ask_service.rs:140-149` 用 `enumerate()` 生成段落标签 `[{i}]`（**0 起**）；而同文件 `:202-213` 的 `AskSource.index = i + 1`（**1 起**）。
- **影响**：模型按 `[0]`、`[1]` 引用，前端 Sources 按 `[1]`、`[2]` 展示 → **引用与来源编号系统性错位一位**，直接违背"引用可下钻"的透明度承诺。
- **建议**：统一为同一基准（推荐上下文也用 `i + 1`，与 Sources 对齐）。

### 1.3【高】Search 页"语义检索"无效 + 降级说明被前端丢弃（静默降级）
- **证据**：
  - `application/search_service.rs:141-165`：请求语义时始终 `method:"lexical"`，把原因放 `SearchResponse.notice`；
  - `src/types/ipc.ts:292-298`：`SearchResponse` **未建模 `notice` 字段**；
  - `src/features/search/SearchPage.tsx` 仅在 `!aiEnabled` 时写死提示，永不展示后端 `notice`。
- **影响**：配了 Key 的用户勾选"语义检索"拿到的是词法结果，且**得不到任何原因说明**；README 又声称语义检索已完成（实际仅 Ask 路径 `retrieval_service` 接了语义），与 Search 页矛盾。
- **建议**：把 `notice` 加入 TS 类型并在 UI 展示；或把语义真正接入 `search`；并修正 README。

### 1.4【中】知识变更类事件"契约存在但从未发出"
- **证据**：`events/app_event.rs:48-74` 定义了 `KnowledgeCommitted / ClaimEvolutionCreated / ConflictDetected / ReviewRequired / SearchCompleted / EmbeddingUpdated`，但全仓搜索显示它们**只在 `name()` 与测试中被引用**，无任何生产 `emit`。
- **影响**：事件契约名存实亡；前端无法据此做"知识已变更"的实时提示与审计。
- **建议**：要么在对应 service 内 emit，要么在文档中降级为"预留"。

### 1.5【中】Ask 上下文缓存指纹不足以反映知识变化
- **证据**：`application/ask_service.rs:285-312` 的指纹只取 `documents/claims` 的 `MAX(时间戳)+COUNT`。**Claim 状态迁移（如 supersede）若不改 `recorded_at` 的 MAX，指纹不变**。
- **影响**：缓存 key 不变 → 可能命中"基于已被取代的 Claim"构建的过期上下文（INV-20/21 意图被绕过）。
- **建议**：指纹纳入 `claims.status` 的分布（如 `SUM(status='superseded')`）或改用 `data_version` PRAGMA。

### 1.6【低】`context_cache_key` 用 `unwrap_or_default()` 吞 DB 错误
- **证据**：`application/ask_service.rs:289-302`。
- **影响**：查询失败时先空串参与哈希，可能造成"不同库状态、相同 key"的碰撞（不只是 miss）。
- **建议**：失败时返回错误 → 退化为必然 miss。

### 1.7【低】`research_tasks.run_id` 被写成 `task_id`
- **证据**：`application/research_service.rs:83-86`，SQL `run_id=?3`，但 `params![task_id, findings, task_id]` → `?3` 绑的是 `task_id`；第 69-72 行算出的 `run_id` 从未使用。
- **影响**：`run_id` 语义错误，与 `agent_runs.id` 无法关联，运行追踪断裂。
- **建议**：`?3` 绑定真正的 `run_id`。

## 2. 领域不变量（"规格声称强制、实际未强制"）

### 2.1【高】`decide` 覆写关系类型后不回滚被取代的 Claim
- **证据**：`infrastructure/claim_relation_repository.rs:199-242`。
  - `relationship_override` 允许改关系类型（`:199`）；
  - 但"置 superseded"只在 `relationship == Supersedes && Accepted` 分支（`:207`），"回滚"只在 `new_status != Accepted` 分支（`:233`）；
  - **"改成非 supersedes 且 Accepted"这一组合两个分支都不覆盖**。
- **影响**：用户先 `accept+supersedes`（target→superseded），再 `accept+relationship=supplements` 重判时，target **永久停留在 `superseded`**，违反 INV-08/INV-09，导致"当前知识/历史"派生长期错误。
- **建议**：用一个真值 `is_accepted_supersedes = relationship==Supersedes && status==Accepted` 统一驱动"记录锚点/置 superseded/回滚"三种副作用。

### 2.2【高】`lifecycle` 兜底把 `rejected/archived/draft` 误标为 `superseded`
- **证据**：`application/knowledge_service.rs:110-114` 用 `derived.get(id).unwrap_or(Lifecycle::Superseded)`；而 `domain/evolution/temporal.rs:106-110` 对 `!participates_in_retrieval()` 的状态直接 `continue`（不进派生表）。
- **影响**：`list_claims(status="rejected")`、查看 rejected Claim 时，卡片 `lifecycle` 显示为 `"superseded"`，**违背"superseded（历史）与 rejected（错误）必须区分"**，前端排序/过滤出错。
- **建议**：禁止 `unwrap_or(Superseded)`；仅当 `claim.status == Superseded` 才标 superseded，被排除的其他状态映射为独立取值。

### 2.3【中】`relations` 写入绕过 INV-14/15/16（归一化引擎未接线）
- **证据**：`infrastructure/relation_repository.rs::insert` 只接收裸 `RelationPredicate`，不校验端点类型、不调用 `normalization::classify`；全仓显示 `normalization::classify` / `allows_relation_row` **仅在测试中被调用**，生产唯一调用点也在 `#[cfg(test)]` 内。
- **影响**：任何未来路径只要调 `insert` 就能写入违反端点类型约束的边，且不会被拦截——"硬规则"实为文档承诺。
- **建议**：把类型校验与归一化判定下沉进 `insert`（或让 `insert` 只接受已校验的 `Relation`）。

### 2.4【中】实体唯一性依赖 SQLite `lower()`（仅 ASCII）
- **证据**：DDL `migrations/0001_init.sql:87` 唯一索引 `lower(name)`；`entity_repository.rs:79-84` 查询同用 `lower()`；而领域侧 `normalize_name`（`domain/ontology/predicate.rs:169-187`）做的是 Unicode 归一，二者不一致。
- **影响**：`Ärzte` vs `ärzte` 可同时插入（INV-03 失效）；大小写/空白差异的名字无法归并，别名消解命中率下降。
- **建议**：新增 `name_normalized` 列（由 `normalize_name` 生成）并对其建 UNIQUE；`find_by_name` 改比归一化列；迁移回填。

### 2.5【低】`decide` 允许 `relationship=unclear` 且 `accepted`（僵尸关系）
- **证据**：`claim_relation_repository.rs:199,244-247`；`unclear` 为合法枚举值，无终态校验。
- **影响**：写出"已接受但什么都没说"的关系，`count_unresolved_conflicts` 与 Review 都不覆盖。
- **建议**：拒绝 `unclear + accepted`。

## 3. 数据安全 / 事务

### 3.1【中】迁移前备份用 `std::fs::copy`，WAL 下备份可能不一致
- **证据**：`application/migration_service.rs:56-69` 只复制 `.db`，未处理 `-wal`；而 `infrastructure/db.rs:35` 全局 `journal_mode=WAL`。
- **影响**：未 checkpoint 前，已提交事务可能只在 `-wal` → **备份缺最近数据**，与"可回滚"承诺不符。
- **建议**：改用 `VACUUM INTO 'backup.db'` 或 SQLite Online Backup API。

### 3.2【中】迁移 `probe` 只探表不探列，可能谎报 `compatible`
- **证据**：`application/migration_service.rs:26-53` 仅 `table_exists`；而 `migration_repository.rs:83-108` 的 `source_claims` 假定 `claims.document_id` 等列存在。
- **影响**：源库列名不同时 `compatible:true` 是假的；`run_migration` 先提交 documents、随后 claims 阶段 `Err`，留下"文档已导入、claim 全无"的半成品。
- **建议**：`probe` 用 `column_exists` 校验必需列并计入 `compatible`；claims 读取失败像 documents 一样进 `notes` 而非中断。

### 3.3【低】`update_ai_settings` 多键写入无事务
- **证据**：`application/settings_service.rs:74-91` 逐键 `set_setting`（各自 autocommit）。
- **影响**：中途失败会留下"一半新一半旧"的 AI 配置。
- **建议**：整组包进一个事务。

## 4. 检索质量

### 4.1【高】LIKE 兜底的"多词 AND"语义实际失效 + 通配符未转义
- **证据**：`infrastructure/fts_repository.rs:160-215`。
  - `:171-175` 每个 term 都生成**一模一样**的子句 `(d.title LIKE ?1 OR d.content LIKE ?1)` 再 `AND`；
  - `:186-188` 只有一个绑定值 `pattern = %<整句>%` → 所有 `?1` 相同 → `X AND X` 等价单条件。
- **影响**：注释声称的 AND 语义未实现；只有"整句连续子串"能命中（搜 `async Rust` 找不到含 `Rust … async` 的文档）；`%`/`_` 未转义，搜 `%` 退化为全表匹配。
- **同类问题**：`entity_repository::list`、`document_repository::list` 的 `format!("%{q}%")` 亦未转义。
- **建议**：每个 term 单独绑定参数（`?1,?2,…`）+ `ESCAPE` 转义。

### 4.2【中】FTS 分支丢弃真实 BM25 分数；`matched_in` 只看正文前 400 字符
- **证据**：`fts_repository.rs:105-151`。SQL 算了 `-bm25(...)` 但 `:146` 用"命中字段数/词数"覆盖；`:109` 用 `substr(d.content,1,400)` 判命中。
- **影响**：长文档后段命中的结果 `score` 归零、`matched_in` 为空，与 LIKE 兜底口径不一致，"为什么匹配"失真。
- **建议**：保留/归一化 BM25 分数；匹配性判定不应基于被截断的内容。

## 5. 前端 / IPC 契约

### 5.1【高】可空字段被 TS 声明为非空 → 渲染 `null` 与死链
- **证据**：
  - `application/dto.rs:236-238` `ClaimCard.sourceDocumentId/Title/sourceQuote` 为 `Option<String>`，而 `src/types/ipc.ts:225-227` 声明为非空；`ClaimCard.tsx:74`、`ClaimDetailPage.tsx:96-97` 直接渲染/拼 `/documents/null`。
  - `application/dto.rs:249-259` `EvidenceCard` 的 `documentTitle/chunkId/startOffset/endOffset` 为 `Option<...>`，而 `ipc.ts:242-254` 非空；`EvidenceList.tsx:23-25,36-38` 渲染 `null–null` / `来源文档：null`。
- **影响**：来源缺失（迁移导入、切片被删）时界面出现 `null` 与死链，与"诚实展示"目标相悖。
- **建议**：TS 类型与契约改为可空，UI 对空值显示「—」或隐藏链接。

### 5.2【高】抽取"逐条接受"可重复提交 → 重复 Claim
- **证据**：`src/features/knowledge/ExtractionPanel.tsx:58-95` 的 `acceptItem/acceptAll` 无 in-flight 状态；后端 `create_claim` 每次 `ClaimId::new()`（`knowledge_service.rs:457`），`claims` 表无去重约束。
- **影响**：双击"接受"或批量进行中再点单条 → 写入重复 Claim，污染知识库并触发多余演化。
- **建议**：前端按条目加 busy 集合禁用按钮；后端对 (subject,predicate,object/content) 做幂等或 UNIQUE。

### 5.3【中】`useAsyncData` 不清旧数据 → 切换实体时脏读
- **证据**：`src/lib/hooks.ts:41-68` deps 变化时只 `setLoading(true)`，不 `setData(null)`；`KnowledgePage.tsx:157-168` 在 `!data` 才显示 loading。
- **影响**：切换实体时旧详情继续显示直到新数据返回；`NOT_FOUND` 时旧数据残留，与 URL 不符。
- **建议**：deps 变化先 `setData(null)`，或用请求参数校验 `data` 一致性。

### 5.4【中】Review 页无法修改关系类型，与 README 闭环不符
- **证据**：`claim_relation_repository.rs::decide` 支持 `relationship` 覆写，`README.md:108` 指引"改成 supersedes 并接受"，但 `src/features/review/ReviewPage.tsx:49-60` 只传 `{relationId, decision}`，页面无该控件。
- **影响**：文档承诺的核心审核能力在 UI 上不存在。
- **建议**：Review 卡片加关系类型下拉并透传 `relationship`；或下调文档描述。

### 5.5【中】`crypto.randomUUID()` 位于 `try` 之外
- **证据**：`AskPage.tsx:57`、`ResearchPage.tsx:70`。
- **影响**：不支持该 API 的 WebView 下点击即抛未捕获异常，表单静默失败。
- **建议**：移入 `try` 或做能力检测回退。

### 5.6【低】契约/字段潜伏问题
- `GraphNode`：Rust 发 `typeName`（`dto.rs:184`），TS 读 `type`（`ipc.ts:197-203`）——当前未消费，属潜伏。

## 7. 建议修复优先级

**P0（数据正确性，优先）**
